# Palace plugins: offline build and SQLite storage

This build kit is versioned in the Core repository under `offline-build/`.
Place checkouts of `Core`, `Creative`, `Lobby`, `PalaceBungee`, `ParkManager`,
`ParkWarp`, `Photopass`, `Pictify`, `RideManager`, `Show`, and `Vanish` in one parent
directory, using those exact checkout names. The build reads sibling sources
without fetching them. Apply the companion PalaceBungee SQLite migration and
Creative PlotPlayer changes from the linked PRs before building.

Build all eleven plugins from `Core/offline-build/`:

```sh
export JAVA_HOME=/path/to/jdk-11-or-newer
./build.sh
```

Python 3 and a JDK are the only installed build prerequisites. `build.py` invokes
`javac` directly, checks the SHA-256 hashes of `vendor/lib/*.jar`, runs the SQLite
integration tests, and packages the plugin JARs in `dist/`. No Maven, Gradle,
package cache, repository, credential, or network connection is used. Set
`PALACE_BUILD_OUTPUT` to choose another output directory. On Windows, run
`python build.py` with `JAVA_HOME` set.

The historical per-plugin Maven POMs describe the original online builds; use
`build.sh` for the offline build. Local plugin sources are compiled together in
dependency order, so no published Palace plugin JAR is required.

## Dependencies and server compatibility

Bundled libraries, origins, checksums, extracted notices, and the PlotSquared v5
source are in `vendor/`. Libraries needed at runtime (including SQLite's JDBC
and native drivers) are embedded in Core and PalaceBungee. Photopass embeds its
HTTP client, and Creative embeds AnvilGUI. Plugin descriptors are generated by
the existing annotation processor; the Bungee descriptor is copied from source.

Minecraft/Bungee, ProtocolLib, WorldEdit, WorldGuard, PlotSquared, TrainCarts,
BKCommonLib, and HolographicDisplays are compile-time APIs, not replacement
server implementations. The existing server plugin requirements still apply.
Creative targets the 1.16 API; the other Bukkit modules retain the 1.12 API.

Audio and Cosmetics are private and are not required by this public build.
The compile-only declarations have been removed. Show skips legacy AudioStart
and AudioSync cues while preserving the visual timeline, and logs this limitation
at startup. Creative runs visual shows without music; park loops and music
selection are unavailable, with existing track/loop files left untouched.
Cosmetics commands and menu buttons explain that the feature is unavailable.
No replacement private plugin implementation is bundled. Every packaged JAR is
checked for private plugin dependencies and private API references in class files.

### Install each JAR on the correct server

- `PalaceBungee.jar` belongs only in the BungeeCord-compatible proxy's plugins
  directory. Do not put it in Paper/Spigot's plugins directory.
- `Creative.jar` targets Minecraft 1.16 and requires compatible PlotSquared v5 and
  WorldEdit 7. Do not install it on Paper 1.12.2. PlotSquared is
  a real public server plugin, not an API supplied by the compiled Creative JAR.
- The other nine Bukkit plugins target the legacy 1.12 API and require the public
  server plugins listed in their descriptors. ParkManager requires both WorldEdit
  and WorldGuard; Photopass requires TrainCarts and BKCommonLib.

The build also writes these deployment notes to `dist/INSTALL.txt`.

Creative now uses PlotSquared's platform-independent `PlotPlayer<?>` interface,
removing its unnecessary dependency on PlotSquared's Bukkit implementation.
ViaVersion is detected through reflection, supporting the legacy and current
API package names without a ViaVersion compile dependency. PalaceBungee uses
the public `ProxyServer` API instead of its internal `BungeeCord` class.

## SQLite configuration

Core `plugins/Core/config.yml`:

```yaml
db:
  path: /srv/palace/palace.sqlite
sql:
  path: /srv/palace/palace-sql.sqlite
```

PalaceBungee `plugins/PalaceBungee/config.yml`:

```yaml
sqlite:
  path: /srv/palace/palace.sqlite
  forum-path: /srv/palace/palace-forum.sqlite
```

Defaults are `palace.sqlite`, `palace-sql.sqlite`, and `palace-forum.sqlite`
relative to the server working directory. **Set Core and PalaceBungee to the
same absolute document database path** when they run on one host and must share
players, parties, bans, queues, servers, and configuration. All dependent plugins
use Core's SQLite connection through its existing document API. MongoDB host,
user, and password settings and MySQL connection URLs are no longer used.

SQLite runs in WAL mode with a 10-second busy timeout. Each document write or
batch uses an immediate transaction; separate connections cannot lose concurrent
increments. Connections close on plugin shutdown. Document content is stored as
extended JSON, preserving ObjectIds and numeric types; UUIDs are stored as
strings. Existing `MongoHandler`, `MongoDatabase`, `MongoCollection`, BSON, and
filter/update types remain as a compatibility facade; no MongoClient is created
and no MongoDB service is contacted. Unsupported facade operations fail
explicitly. Filters are evaluated in Java within a collection, so large datasets
will need query/index work before high-volume production use.

SQLite is a local file database. Sharing a file over a network filesystem or
between different hosts is not a supported replacement for the old distributed
MongoDB setup. RabbitMQ, dashboards, and other service integrations are
unchanged; an offline **build** does not make every runtime feature offline.

## Import existing data

No database credentials or existing data were supplied here. The application now
initializes SQLite; transferring production data is a separate offline import.
Stop writers and export **each** Mongo collection with `mongoexport` using its
default JSON-lines format, naming the files `<collection>.json` or `.jsonl` in
one directory. Do not use `--jsonArray` or binary `mongodump` files. Then run:

```sh
java -cp dist/Core.jar network.palace.storage.ImportMongoExport \
  /srv/palace/new-palace.sqlite /path/to/exports
```

The importer preserves collection names, ObjectIds, documents, nested arrays,
and numeric types. Standard and legacy Java BSON UUID binaries become UUID
strings. It stages the whole import before publishing the database, refuses an
existing destination, and removes its staging files on failure. Check the printed
counts and resulting records, then configure both servers to use the imported
file. Keep the original databases and exports until the deployment is validated.

Core/Pictify's SQL file initializes `pictify(id INTEGER PRIMARY KEY, source TEXT)`.
The forum file initializes `core_members(member_id, email, member_group_id)` and
`core_pfields_content(member_id, field_2, field_3, field_4)`. To migrate those legacy
MySQL tables, export the corresponding columns to CSV and use
`python tools/import-sql-csv.py <new.sqlite> <pictify|forum> <csv-directory>`.
The forum SQLite file must be kept in sync with the forum application if that
application still uses a separate database; changing the plugin does not migrate
the external forum software.

## Verification

Every build runs real SQLite tests covering shared connections, updates,
upserts, arrays and positional moderation updates, projections, sorting,
leaderboards, batch rollback, concurrent increments, restart persistence, and
safe export import. The tests also run against the packaged Core JAR with no
external classpath, checking that the SQLite runtime is embedded correctly.
Minecraft server behavior still needs a deployment smoke test with its actual
runtime plugins and configuration.
