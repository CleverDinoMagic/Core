# Palace plugins: offline build and MySQL storage

This build kit is versioned in the Core repository under `offline-build/`.
Place checkouts of `Core`, `Creative`, `Lobby`, `PalaceBungee`, `ParkManager`,
`ParkWarp`, `Photopass`, `Pictify`, `RideManager`, `Show`, and `Vanish` in one parent
directory, using those exact checkout names. The build reads sibling sources
without fetching them. Apply the companion PalaceBungee MySQL migration and
Creative PlotPlayer changes from the linked PRs before building.

Build all eleven plugins from `Core/offline-build/`:

```sh
export JAVA_HOME=/path/to/jdk-11-or-newer
./build.sh
```

Python 3 and a JDK are the only installed build prerequisites. `build.py` invokes
`javac` directly, checks the SHA-256 hashes of `vendor/lib/*.jar`, runs the local document
regression tests and optional MySQL integration tests, and packages the plugin JARs in `dist/`. No Maven, Gradle,
package cache, repository, credential, or network connection is used. Set
`PALACE_BUILD_OUTPUT` to choose another output directory. On Windows, run
`python build.py` with `JAVA_HOME` set.

The historical per-plugin Maven POMs describe the original online builds; use
`build.sh` for the offline build. Local plugin sources are compiled together in
dependency order, so no published Palace plugin JAR is required.

## Dependencies and server compatibility

Bundled libraries, origins, checksums, extracted notices, and the PlotSquared v5
source are in `vendor/`. Libraries needed at runtime (including MySQL Connector/J and the legacy SQLite
import driver) are embedded in Core and PalaceBungee. Photopass embeds its
HTTP client, and Creative embeds AnvilGUI. Plugin descriptors are generated by
the existing annotation processor; the Bungee descriptor is copied from source.

Minecraft/Bungee, ProtocolLib, WorldEdit, WorldGuard, PlotSquared, TrainCarts,
BKCommonLib, and HolographicDisplays are compile-time APIs, not replacement
server implementations. The existing server plugin requirements still apply.
Creative targets the 1.16 API; the other Bukkit modules retain the 1.12 API.

Audio and Cosmetics are private and are not required by this public build.
The compile-only declarations have been removed. Show skips legacy AudioStart
and AudioSync cues while preserving the visual timeline, and logs this limitation
at startup. Creative runs visual shows without music; park loops and music
selection are unavailable, with existing track/loop files left untouched.
Cosmetics commands and menu buttons explain that the feature is unavailable.
No replacement private plugin implementation is bundled. Every packaged JAR is
checked for private plugin dependencies and private API references in class files.

### Install each JAR on the correct server

- `PalaceBungee.jar` belongs only in the BungeeCord-compatible proxy's plugins
  directory. Do not put it in Paper/Spigot's plugins directory.
- `Creative.jar` targets Minecraft 1.16 and requires compatible PlotSquared v5 and
  WorldEdit 7. Do not install it on Paper 1.12.2. PlotSquared is
  a real public server plugin, not an API supplied by the compiled Creative JAR.
- The other nine Bukkit plugins target the legacy 1.12 API and require the public
  server plugins listed in their descriptors. ParkManager requires both WorldEdit
  and WorldGuard; Photopass requires TrainCarts and BKCommonLib.

The build also writes these deployment notes to `dist/INSTALL.txt`.

Creative now uses PlotSquared's platform-independent `PlotPlayer<?>` interface,
removing its unnecessary dependency on PlotSquared's Bukkit implementation.
ViaVersion is detected through reflection, supporting the legacy and current
API package names without a ViaVersion compile dependency. PalaceBungee uses
the public `ProxyServer` API instead of its internal `BungeeCord` class.

## Required RabbitMQ messaging configuration

RabbitMQ is required at runtime even though compilation is offline and persistence uses MySQL. In `plugins/Core/config.yml`, configure `rabbitmq.host`,
`rabbitmq.username`, and `rabbitmq.password` with your existing broker's actual
settings. The bundled configuration leaves these values blank; it does not
supply or fall back to guest credentials. `rabbitmq.port` defaults to AMQP port
5672 and `rabbitmq.virtualhost` defaults to `/`; set the virtual host your broker
user can access. Ports must be YAML integers in the range 1–65535.

The configuration loader reads defaults from Core's bundled resource without
replacing the server's config file or operator credentials. Old configurations
therefore receive the standard port/virtual-host defaults, but missing credentials
still require operator input. Missing sections, blank settings and invalid types
produce a diagnostic naming the exact config keys and file, without printing
credentials. Failed connections or required queue setup stop Core startup with
an explicit error rather than running with messaging unavailable. Broker users
need permission to declare and use the required exchanges/queues in that virtual
host. No broker is started or credentials created by Core.

## MySQL configuration

MySQL 8.4 is the tested persistence backend. Core, PalaceBungee, and all plugins
using Core's document API store their data in MySQL. Core/Pictify's SQL API and
proxy forum linking also use MySQL. No MongoDB service or SQLite file is used by
the running plugins. SQLite support remains only for legacy import and tests.

Create an empty MySQL schema (for example `palace`, using `utf8mb4`) and an account
with SELECT, INSERT, UPDATE, DELETE, and CREATE privileges on that schema. Put the
same settings in `plugins/Core/config.yml` on each backend and
`plugins/PalaceBungee/config.yml` on the proxy:

```yaml
mysql:
  host: 'your-mysql-host'
  port: 3306
  database: palace
  username: 'your-mysql-user'
  password: 'your-mysql-password'
  ssl-mode: PREFERRED
```

The schema and account must already exist. The plugin creates its own InnoDB
tables, but does not create databases, database users, or broker credentials.
Missing credentials and invalid types produce errors naming the config keys.
Old `db.path`, `sqlite.path`, and MongoDB connection settings are ignored.
PalaceBungee adds missing template fields to existing configs while preserving
operator values; Core supplies bundled defaults without rewriting its config.
Fill in all five MySQL fields before enabling the updated plugins.

All servers can now connect to the same MySQL schema across hosts. Credentials
are passed separately from the JDBC URL. HikariCP manages/replaces pooled
connections; connect, acquisition, and socket timeouts are bounded. `ssl-mode`
accepts MySQL Connector/J's DISABLED, PREFERRED, REQUIRED, VERIFY_CA, or
VERIFY_IDENTITY modes; choose the mode appropriate for your MySQL deployment and
configure trusted certificates when verifying identity.

The main schema also contains Pictify's `pictify` table. To use a separate Pictify
schema, add a full `sql` section to Core with the same six fields as `mysql`.
For forum linking, point PalaceBungee's optional `forum-mysql` section at the
forum application's existing MySQL schema (the same six fields). If absent,
forum linking uses `mysql`. The forum application must supply `core_members`
and `core_pfields_content`; PalaceBungee does not create or alter forum tables.

The existing `MongoHandler`, BSON, filters, and collection interfaces remain as a
compatibility API for dependent plugins; they do not connect to MongoDB. Extended
JSON documents are stored in `palace_documents`, with case-sensitive collection
names and hashed BSON IDs. Writes lock an InnoDB row per collection, then read and
modify documents in one transaction, preventing lost concurrent increments or
upserts across servers. Import uses one transaction for all documents.
Unsupported document API operations still fail explicitly. Filters are evaluated
in Java within each collection; large datasets need query/index work before
high-volume use, and writes in one collection are serialized.

## Import existing document data

Stop application writers and back up the source. Import into a new, empty MySQL
schema before starting any plugins; the importer refuses a non-empty document
store. A failed import rolls back all inserted documents. The empty schema/tables
may remain after failure because MySQL DDL commits separately.

Create a local UTF-8 properties file with these keys, using the target schema's
credentials (do not commit it):

```properties
mysql.host=your-mysql-host
mysql.port=3306
mysql.database=palace
mysql.username=your-mysql-user
mysql.password=your-mysql-password
mysql.ssl-mode=PREFERRED
```

Java properties escaping applies; escape literal backslashes in passwords.
For MongoDB, export each collection with `mongoexport` in default JSON-lines
format, naming files `<collection>.json` or `.jsonl`. Then run:

```sh
java -cp dist/Core.jar network.palace.storage.ImportMongoExport \
  /private/mysql.properties /path/to/exports
```

Do not use `--jsonArray` or binary `mongodump` files. The importer retains
collection names, ObjectIds, nested arrays, numeric types, and normalized UUIDs.
For a document SQLite file produced by the earlier version, use:

```sh
java -cp dist/Core.jar network.palace.storage.ImportSQLite \
  /private/mysql.properties /path/to/palace.sqlite
```

The SQLite source is opened read-only. Do not import both copies of the same
source data. Keep the original databases and exports until login and persistence
are verified in the real server deployment. Existing MySQL forum tables remain
in place; configure their schema instead of exporting/reimporting them.

SQLite Pictify/forum relational tables are separate from the document store.
Use `ImportSQLiteTables <mysql.properties> <pictify|forum> <legacy.sqlite>` to
copy them to existing empty MySQL tables with matching columns. Create Pictify's
table by starting Core against the new schema first; forum tables must already
be installed by the forum application. This import also rolls back on failure.
The older CSV-to-SQLite script is retained only as a legacy conversion utility;
it is not the runtime persistence configuration.

## Verification

The offline build runs the shared document engine regression suite using SQLite
as a local fixture, plus MySQL configuration and packaged-runtime checks. To run
real MySQL integration tests, create a dedicated empty schema whose name begins
`palace_test_`, configure it in a private properties file, and run:

```sh
PALACE_MYSQL_TEST_CONFIG=/private/mysql-test.properties ./build.sh
```

**Use only a disposable test schema:** these tests delete their fixture
collections. With that variable set, checks run against real MySQL for shared
connections, nested updates, upserts, arrays, positional moderation updates,
projections, sorting, leaderboards, rollback, concurrent increments, reconnecting
stores, case-sensitive IDs, utf8mb4, empty-player login, JSON-lines imports, and
SQLite-to-MySQL migration. The MySQL tests also run against packaged Core and
PalaceBungee JARs without an external driver classpath, proving Connector/J is
embedded. Without that variable the build explicitly reports that MySQL
integration checks are skipped; compilation still requires no network or server.
Minecraft server behavior and broker access still require deployment smoke tests.
